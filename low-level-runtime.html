Telomare’s Low-Level Runtime

A loop in C that fires the interaction net’s rules on a flat array of words: what it is, how it stays faithful to the Bend definition, what it gains, and what is still on paper. A companion to The Net That Counts Itself, the primer on the net itself.

In short. The low-level runtime today is one thing: the C loop behind --ic, in bend/effs/ic.c. It exists only in the Bend port; Haskell master has no low-level code at all. Assembly, many cores and the GPU are designed but not started. A plain run and --fast, where long programs actually run, don’t use it.

State of this document. It describes branch rt, which is local and unpushed. Section 9 says which part is where.

1Where it sits

The telomare command has three runtimes, as master does. Only one runs on the net, and only that one has low-level code.

ModeRuns onLow-level code
plain, --meterbend/Reference.bend, the reference evaluatorNone
--fastbend/Fast.bend, the unsized interpreterNone
--icbend/IC.bend’s netThe C loop

The C is a Bend foreign effect, nt.reduce, declared in bend/Native.bend. A def with a foreign body fails Bend’s proof gate, so the code is split in two. Main.bend holds the whole command and takes its runner as a template. Main.main passes the pure IC.run and stays proof-checked; Native.main passes the C loop, and that is the binary the flake ships. Everything.bend, which checks every module, does not import Native.bend. On the JavaScript target ic.js fires nothing and hands every pair back, so Bend does all the work.

2The machine: a net as words

The net is one Array<U32>, the same array in Bend and in C, so crossing the boundary copies nothing. Each agent is eight words. A port is agent*4 + slot, so p = 41 is agent 10, slot 1, and its peer is in word 10*8 + 1 + 1 = 82. Agent 0 is never used, so 0 ends the free list.

A second array, the template store, holds what never changes during a run: each closure’s code as a template (agents and wires, instantiated when the closure is applied), the constants (closed data, two words per pair, with equal data shared), and the plans that guide copying. The rest of the state is a few words: stack pointer, bump, free-list head, next label, fuel and error.

Allocation is part of the meaning

alloc takes the last agent freed, else the next unused one, and doubles the array when it is full. The C must do this in exactly IC.bend’s order, because the test compares whole nets word for word. That is also why DUP_ABORTED allocates a fourth agent nothing uses: IC.bend’s alloc4 does, and so the net has to match.

3The loop

This is the whole of it, slightly trimmed from nt_reduce. Pop a pair, skip it if it went stale, look up the rule, try the other order if there is none, fire.

while (x->err == 0 && x->sp != 0) {
  u32 top = x->sp - 1;
  u32 a = x->m[top * 8 + 6], b = x->m[top * 8 + 7];
  u32 ka = x->m[a * 8],      kb = x->m[b * 8];
  if (ka == 0 || kb == 0 || x->m[a * 8 + 1] != b * 4 || x->m[b * 8 + 1] != a * 4) {
    x->sp = top;               // stale: one of them is gone or rewired
    continue;
  }
  u8 r = nt_rule[ka][kb];      // n first, as IC.bend tries it
  if (r == NT_NONE) { r = nt_rule[kb][ka]; /* n and m swap */ }
  if (r == NT_NONE || r == NT_BEND) return;      // Bend's to fire
  if (r == NT_APPLY_REF && nt_limit(j.b)) return; // a --fast step: Bend counts it
  x->sp = top;
  nt_apply(x, r, n, i, m, j);  // the rule
}

The loop stops at the first pair it won’t fire, and leaves that pair on the stack. Native.bend pops it, fires it with IC.bend’s own fire, and calls the C again. Three things go back to Bend:

  • the five rules that make a stuck value, because the message is a Bend String;
  • an applied unbounded-recursion step, because --fast’s unroll count lives in Bend’s cold state;
  • a pair with no rule, because the error message is built in Bend.

Guided copying is the odd one out

Every rule above is a fixed, local rewrite except DUP_PLANNED’s closure branch. Copying a closure whose code has a published capture layout walks a whole region of the net in one interaction (nt_region), led by the plan: it copies what the plan vouches for and leaves a Dup at each frontier. It costs one unit of fuel however much it walks, and in the profile it is about 13% of a run. It is the main thing that isn’t local, which matters for many cores.

5One description of the rules

The design from 2026-10-27 says every back end is “generated from or checked against” one description. Until today ic.c was only checked: a hand-written second copy of the rules, with assembly and the GPU set to be a third and a fourth. Branch rt makes the “generated” half real.

  • bend/Rules.bend: act gives each rule as data, in IC.bend’s order. It is a total match on IC.bend’s Rule, so a new rule fails to check until the table has it.
  • bend/dev/genic.bend: prints ic.c with its marked parts regenerated, the dispatch from IC.bend’s rule.of and the bodies from the table. A flake check fails if the file differs.

What the table can’t express

Whether a table could express the rules was an open question. They turned out to be a small language: spend, delete, new agent, new label, read a constant’s part, wire, plus one branch on labels and one on plans. The rest of ic.c is not rules but the machine under them, and it stays by hand:

  • the net’s words: alloc, delete, connect, grow;
  • instantiate, which the table names as one step;
  • guided copying, region, which the table also only names;
  • the loop, including the --fast step test.

So of ic.c’s 651 lines, 281 are now printed. A new back end would still write the machine by hand once, and get the rules printed. That is less than a full generator, and it is the honest size of the win so far: it removes the rule copies, not the machine copies.

6How we know it’s right

Almost all of this is testing, not proof. Foreign code can’t pass the proof gate, so nothing proves the C correct, and nothing proves the table equal to IC.bend.

A gap this work found

Counting firings in the C showed that 6 of its 21 rules had never fired in the word-for-word test: PASS_APP, SPLIT_ABORTED, SPLIT_STUCK, ERA_ABORTED, DUP_ABORTED and DUP_DUP. The sessions just never reach them. Both tests now have a group where every two kinds meet alone on a net, and all 21 rules fire.

To check that the new groups can fail, one wire of commuting Dups was crossed in the table and the C regenerated:

ok   rules-terms      ok   native-terms
FAIL rules-pairs      FAIL native-pairs
ok   rules-sessions   ok   native-sessions

The sessions alone would have passed that bug. One mutation doesn’t prove the suite complete: the pairs group leaves APPLY_REF and OPEN to the sessions, since those read the store, and the error paths in nt_region have no test that reaches them.

What these gains cost

  • .telc files grew. Tic-tac-toe’s went from 265 KB to 458 KB, and simpleplus’s from 62 KB to 155 KB, because they now hold the prepared programs. Version 9 files are refused and need recompiling.
  • The generated C is about 3% slower than the hand-written one: 339M cycles against 328M, and 1% more instructions, measured under load. The cause isn’t known yet. Inlining nt_dup_pair into the switch added 5% instructions, so the printer keeps it out of line.
  • Compile time is unchanged and still slow. Tic-tac-toe takes the port 110–190 s, depending on load, and master 72 s. This is outside the runtime, but it is the longest wait a user sees.

8What’s still on paper

N3: assembly

The profile’s hot paths are the candidates: the dispatch, split-pair, setenv-pair, instantiation and dup copying, printed from the same table and held to the same word-for-word test. The gain should be modest, because clang already compiles this loop and it has no obvious waste. That is an estimate; nothing has been measured.

N4: many cores

The plan: per-thread pair stacks and free lists, per-thread label ranges, atomic linking. IC.bend’s header claims each rule consumes the pair it fires, so the count doesn’t depend on firing order, which is what makes this possible. That claim isn’t proved, and no test fires pairs in a different order. Two things need design first: guided copying walks a whole region in one rule, and the free list and label counter are global. The word-for-word test would also have to give way to comparing read-back and counts.

N5: the GPU

Bend’s own GPU targets are CUDA and Metal only. olimpo’s RX 580 has no CUDA, and ROCm no longer supports it. Vulkan compute through RADV runs on it with the 64-bit integers we need (checked 10-27, but no net has run on it), and OpenCL through Mesa’s rusticl is untried. A net suits a GPU best as many independent nets at once, one session per work-group, rather than one turn’s mostly sequential net. The path is your choice and can wait until N5.

The biggest limits, whichever comes next

  • The fuel cap. A turn stops at 10M interactions by default, about 0.3 s. So faster hardware can save little per turn on today’s programs unless that cap rises.
  • Long runs don’t reach this code. They run on --fast, an interpreter written in Bend. It takes 8.2 s for 9! where the 10-27 master build took 4.7 s. It has no C and is the one place the port is slower at run time.
  • The machine is still hand-written. See section 5.
